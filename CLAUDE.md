# CLAUDE.md

Инструкции для Claude Code при работе в этом репозитории. Полный план реализации
и обоснование решений — в `implementation-plan.md`, структура системы — в
`ARCHITECTURE.md`. Этот файл — только рабочие правила, не дублирует их содержимое.

## Что это за проект

Личное приложение планирования питания. Backend на Python — единственный
источник истины для расписания блюд, начисления ккал/белка и списка покупок.
Frontend — презентационный слой, ничего не пересчитывает сам.

## Окружение и команды

- Менеджер пакетов — **uv**, раскладка `src/`. Пакет: `src/meal_planner/`
  (подпакеты `core/`, `db/`, `api/`). Тесты — в `tests/` на верхнем уровне.
- `uv sync` — установить зависимости; `uv run pytest` — тесты;
  `uv run ruff check .` — линтер;
  `uv run uvicorn meal_planner.api.main:app --reload` — dev-сервер.
- Зависимости добавлять только через `uv add` (и `uv add --dev`), не править
  `uv.lock` руками. Импорты всегда абсолютные: `from meal_planner.core...`.
- Путь к БД, порт, каталог статики — только из переменных окружения
  (`MEALPLAN_DB_PATH`, `MEALPLAN_PORT`, `MEALPLAN_STATIC_DIR`), не хардкодить.
- Frontend — `frontend/` (Vite + React, Node 24 через fnm; системный node —
  v12, не нужен ни для чего: golden-харнессы `tools/golden/` на Node 24 дают
  побайтово те же фикстуры). Из `frontend/`: `npm ci`, `npm run dev` (прокси `/api` на :8000),
  `npm test` (vitest), `npm run build` → `frontend/dist`. После изменения
  схем в `api/schemas.py` — `npm run gen:api` (снапшот `openapi.json` +
  `src/api-types.ts`; `tests/test_openapi_snapshot.py` ловит устаревший).
  После изменений в том, что отдаёт `/api/state`, — `npm run gen:fixtures`
  (фикстуры UI-снапшотов, `tests/test_ui_fixtures.py` ловит устаревшие).
  Сознательное изменение UI — `npx vitest run -u` в том же коммите
  (снапшоты `src/__snapshots__/` в git).
  Фронтенд только рисует `AppState` — `src/no-business-logic.test.ts`
  не ослаблять.
  Новые npm-зависимости — только версии старше двух недель
  (`npm install --before=<дата>`).
- `meal-plan.jsx` в корне — замороженный исторический эталон, с которого
  сняты Python-golden (`tools/golden/`, sha256 в `tests/golden_*.py`), не
  править. Фронтенд-тесты его больше не импортируют (6.1). Рабочая копия —
  `frontend/src/MealPlanApp.jsx`.
- Бэкап БД — `meal-planner-backup` (entry point, `db/backup.py`). Пакет HA —
  `ha/packages/meal_planner.yaml`. Развёртывание рядом с HA, обновление и
  восстановление — README, «Развёртывание рядом с Home Assistant».

## Порядок работы

Используй `codegraph_explore` MCP tool перед началом составления плана, исполнения задач по кодингу и исследлвания кода.

Реализовывать строго по фазам из `implementation-plan.md`, раздел
"Фазы реализации" — одну фазу за один заход, не забегая вперёд:

1. Доменный слой (`core/`) + golden-тесты — без FastAPI, без SQLite.
2. Backend API (FastAPI + SQLite), синхронная модель без WebSocket.
3. Frontend rewiring — убрать JS-расчёты, подключить к API.
4. (опционально) push-обновления.
5. Рецепты в БД и редактирование через UI (справочник ингредиентов, слоты цикла).
6. Тюнинг после порта — поведение меняется сознательно (см. ниже).
7. Интеграция с Home Assistant — HA в Docker (HA Container, без
   Supervisor/add-on'ов): отдельный контейнер рядом с HA + YAML-пакет для Assist.
   Сделана (2026-10); `custom_component` (7.10) — только если YAML не хватит.
8. Питание и HA: цель по ккал, остатки в холодильнике, разнообразие цикла,
   рецепты от Assist — в основном после фазы 5.
9. Рецепты на дашборде «Кухня»: книга рецептов в API и сенсор HA, вид
   Metro — в HA-репо (`TICKETS-HA.md`, MT-10…MT-13).
10. Готовка по ингредиентам на «Рецептах»: журнал списаний, действия
    готовки, вёрстка — MT-14…MT-16 в HA-репо.

Тикеты фаз 5–10 — в `TICKETS.md`. С фазы 6 эталон — правила Python-версии, а
не совпадение с `meal-plan.jsx`. Тикет, меняющий бизнес-правило, явно
перечисляет, какие golden-фикстуры и снапшоты обновляются. Это и есть
«явное указание» для правила о golden-тестах ниже.

Не начинать следующую фазу, пока тесты предыдущей не зелёные.

## Жёсткие правила (не нарушать без явного запроса)

- **Никакой бизнес-логики во фронтенде.** Ротация блюд, даты закупки, суммы
  ккал/белка, агрегация ингредиентов — только в `core/`. Если кажется, что
  "быстрее посчитать в компоненте" — это неверный путь, см. `implementation-plan.md`
  → "Избегать".
- **Golden-тесты обязательны перед переносом любой логики ротации/агрегации**
  из `MealPlanApp.tsx`. Если контрольных примеров ещё нет — сначала снять их
  с текущего работающего JS-поведения, потом писать Python-версию.
- **Мутации — только через атомарные action-эндпоинты** (`/api/actions/...`),
  не через универсальный diff настроек. Если для новой фичи не находится
  подходящего атомарного действия — обсудить с пользователем, не изобретать
  generic-эндпоинт по умолчанию.
- **Расписание и список покупок не кэшировать в SQLite** — только `settings`.
  Всё остальное — `planner.recompute()` на лету.
- **Во фронтенде только относительные URL** (`fetch('api/state')`, не
  `/api/state`) и `base: './'` в Vite — приложение должно работать за
  Home Assistant Ingress под произвольным префиксом.
- **WebSocket/SSE не добавлять**, пока явно не попросят (см. фазу 4 — опционально).

## Стиль и структура кода

- `core/` — чистый Python, без импортов FastAPI/Pydantic/SQLite и без
  импортов `meal_planner.api` / `meal_planner.db`. Тестируется без поднятия
  сервера. Граница проверяется `tests/test_architecture.py` — не отключать
  и не ослаблять этот тест.
- Один Python-пакет. Не создавать uv workspace и не выносить `core` в
  отдельный дистрибутив.
- Идентификаторы рецептов (`l1`, `d3`, `b2` и т.п.) сохранять как в оригинале —
  это ключи, на которые ссылается уже существующий фронтенд-код и данные.
- С фазы 5 рецепты, справочник ингредиентов и состав цикла — в SQLite, а не
  константы: `core/` получает `Catalog` параметром (`recompute(catalog, …)`),
  API читает его из БД на каждый запрос. `recipes_data.py`, `nutrition.py`
  (`PER_100G`, `GRAMS_PER_UNIT`), `STORE_PIECES`, `seed.LUNCH_IDS` — только
  сид миграции 2 и основа golden (`SEED_CATALOG`): их правка живую БД не
  меняет (сид прошёл один раз). Живые данные меняются действиями или новой
  миграцией.
- Схема БД — только новой функцией в конце `db/schema.MIGRATIONS`
  (`PRAGMA user_version`); прошедшие миграции не править.
- Соответствие JS → Python функций — см. таблицу в `implementation-plan.md`
  раздел 3. Портировать 1:1, не "по смыслу".

## Home Assistant

- Add-on/Supervisor не предполагать: у пользователя HA Container. Приложение
  слушает только `127.0.0.1:8001` на хосте — аутентификации в API нет и не
  нужно, пока порт не открыт в сеть.
- Пакет `ha/packages/meal_planner.yaml` — клиент API. При изменении схем
  `/api/summary` или действий обновлять пакет в том же коммите;
  `tests/test_ha_package.py` сверяет его с `frontend/openapi.json` — не
  ослаблять.
- Новое действие для Assist — правило в `core/`, атомарный эндпоинт,
  `rest_command`, скрипт с `description` и `fields` (из них LLM строит tool),
  кнопка в UI, если действие видно в приложении.
- LLM в Assist видит состояние сущностей, но не их атрибуты (белый список
  HA). Данные для модели — ответом скрипта (`stop` + `response_variable`).
- В шаблонах Jinja — `x['items']`, не `x.items` (это метод dict).
- Конфиги HA на хосте — отдельный git-репо, его коммитит пользователь
  (отдельное сообщение коммита). `secrets.yaml` и `.storage/` не читать.

## Тесты

- Golden-тесты (`test_scheduling.py`) — не менять ожидаемые значения без
  явного указания, что бизнес-правило действительно поменялось.
- После фазы 3 эталон — правила Python-версии, а не `meal-plan.jsx`.
  Явное указание — тикет фазы 6, перечисляющий обновляемые фикстуры;
  новые ожидания записывать как правило, не перегенерировать из JSX.
