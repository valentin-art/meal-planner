# TICKETS.md

Разбивка `implementation-plan.md` на тикеты по 1–2 часа — чтобы можно было
закрывать по одному в свободные окна между другими проектами, не теряя нить.
Внутри фазы — по порядку, между фазами можно не торопиться (см. прогноз в
обсуждении сроков). Каждый тикет — отдельный коммит/PR.

Чек-боксы — отмечайте по ходу, файл живёт в репозитории.

---

## Фаза 0 — Скаффолдинг (1–1.5 ч)

- [x] **0.1** Инициализировать проект через uv с раскладкой `src/`:
      `uv init --package meal-planner` (или вручную), `requires-python >=3.12`,
      пакет `src/meal_planner/` с подпакетами `core/`, `db/`, `api/` (пустые
      `__init__.py`), каталог `tests/`. Зависимости: `uv add fastapi
      "uvicorn[standard]"`, dev-группа: `uv add --dev pytest httpx ruff`.
      В `pyproject.toml` — конфиг pytest (`testpaths = ["tests"]`) и ruff.
      Закоммитить `uv.lock`. Проверка: `uv run pytest` запускается без ошибок
      на пустой папке тестов, `uv run python -c "import meal_planner"` работает.
      Перенести в корень репозитория `CLAUDE.md`, `ARCHITECTURE.md`,
      `TICKETS.md`, `implementation-plan.md`.

## Фаза 7 — Home Assistant (HA Container)

HA установлен **в Docker (HA Container)**: Supervisor'а нет, а значит нет
add-on'ов, Ingress и бэкапов add-on'ов. Приложение — отдельный контейнер
рядом с HA, HA — его клиент по HTTP.

Цель:
- контейнер meal-planner работает рядом с HA и переживает перезапуски;
- UI открывается из боковой панели HA;
- БД регулярно бэкапится;
- Assist отвечает на «что сегодня на обед», «когда закупка» и выполняет
  действия вроде «пропусти готовку».

Схема и варианты — `implementation-plan.md`, «Home Assistant integration».
Python-компонент (`custom_component`) — только если YAML не хватит. Если HA
когда-нибудь переедет на HAOS, путь через add-on описан там же.

## Фаза 8 — Питание и HA: остатки, разнообразие, калорийность

Идеи пользователя (2026-10-26). Поведение меняется сознательно, как в
фазе 6: тикет, меняющий правило, перечисляет обновляемые фикстуры. Без новых
настроек поведение прежнее.

Зависимости:
- 8.1 — сразу после фазы 7;
- 8.2–8.6 — после фазы 5 (справочник ингредиентов и пул рецептов);
- 8.6 — последним.

Решения, помеченные «предложено», подтвердить при старте тикета.

- [ ] **8.1** *(2–3 ч)* Цель по калорийности: показать отклонение.
      - Настройка `daily_kcal_target`; по желанию — цель по белку.
        Действие `set-nutrition-target`.
      - `core/`: отклонение дня от цели. UI: в дне и в «Меню».
        `/api/summary` и сенсор HA: «≈ 1790 ккал (−210)».
      - Предложено: начать с отображения, без изменения блюд и порций.
- [ ] **8.2** *(3–4 ч)* Остатки (холодильник) и покупки за вычетом
      остатков.
      - Таблица `stock`: ингредиент справочника → количество в его единице.
        Действия `set-stock-item` и `clear-stock`.
      - `core/`: покупка = нужно по плану − остаток, по ключу `name|unit`,
        не меньше 0. «≈ N шт» пересчитывается от остатка.
      - UI: вкладка «Холодильник».
      - HA: `rest_command` и скрипты для Assist («у меня 6 яиц»).
        `fridge.yaml` (`input_number` молоко, яйца, сыр) заменить или
        синхронизировать в одну сторону.
      - Синхронизация to-do (7.8) получает уже уменьшенный список, её
        менять не нужно.
      - Предложено:
        - источник истины — приложение, HA только читает и пишет через
          действия;
        - остатки вводятся вручную, автосписания при готовке нет — учёт
          быстро разошёлся бы с реальностью.
- [ ] **8.3** *(1–2 ч, опционально)* Купленное — в остатки.
      - Автоматизация HA: пункт to-do с меткой `meal-planner` отмечен →
        `add-stock`.
      - Имеет смысл только вместе со списанием при готовке, иначе остатки
        только растут. Решить: списывать ли автоматически приготовленное в
        день готовки (`core/` знает, что готовится) или отказаться от 8.3.
- [ ] **8.4** *(3–5 ч)* Разнообразие: перемешанный порядок и новые рецепты
      из пула.
      - Случайность с зерном: `settings.shuffle_seed`. Тогда
        `recompute` остаётся чистой функцией и план воспроизводим. Действие
        `reshuffle-cycle` меняет зерно.
      - Перемешиваются только циклы, под которые ещё не было закупки.
        Правила рыбы (6.6) и сроков хранения соблюдаются.
      - «Новые рецепты» — выбор из пула рецептов фазы 5 (рецептов больше,
        чем слотов) на каждый цикл.
      - По умолчанию выключено: golden не меняются.
      - Предложено: зерно в настройках.
- [ ] **8.5** *(3–4 ч)* Подбор под калорийность (после 8.1, фазы 5 и,
      для выбора блюд, 8.4).
      - (б) Масштаб порций: множитель рецепта, чтобы день попадал в цель.
        Меняет количества в покупках.
      - (в) Выбор блюд из пула под цель при перемешивании.
      - Начать с (б); (в) — если понадобится.
- [ ] **8.6** *(3–5 ч)* Рецепт от Assist из имеющихся продуктов.
      - Скрипт-tool отдаёт модели остатки (8.2) и справочник ингредиентов.
        LLM предлагает рецепт, скрипт вызывает `save-recipe` со статусом
        «черновик».
      - Ингредиенты — только из справочника: незнакомый — отказ с
        предложением добавить. Ккал и белок считает `core/`, не модель.
      - Черновик попадает в пул или в слот цикла только после
        подтверждения в UI — ошибка модели не должна оказаться в списке
        покупок.
      - Зависит от фазы 5, 8.2 и пакета HA (7.6).

**Готовность фазы:** видно отклонение от цели по ккал; покупки учитывают
холодильник; цикл можно разнообразить, не ломая уже купленное; Assist
предлагает рецепт из того, что есть, а он попадает в план только после
подтверждения.
