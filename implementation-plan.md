# План реализации: Meal Plan с Python-ядром

## Конвенции проекта

- **Менеджер пакетов — `uv`**, раскладка `src/`. Один Python-пакет
  `meal_planner` с подпакетами `core/`, `db/`, `api/`. Зависимости и конфиг
  pytest/ruff — в `pyproject.toml`, версии зафиксированы в `uv.lock`.
- Дальше в документе `core/`, `db/`, `api/` без префикса означают
  `src/meal_planner/core/` и т.д.; пути к файлам указаны полностью.
- Запуск: `uv run pytest`, `uv run uvicorn meal_planner.api.main:app`.
- Конфигурация приложения (путь к БД, порт, каталог статики) — только через
  переменные окружения с разумными значениями по умолчанию (см. раздел
  "Упаковка и запуск").

## Цель

Перенести всю логику планирования (сейчас — в JS-функциях внутри `MealPlanApp.tsx`)
в полноценное Python-ядро с явными доменными структурами данных. Frontend перестаёт
что-либо считать сам — он только отправляет намерения пользователя (intents) и
отображает состояние, которое строит бэкенд.

## 0. Принцип взаимодействия (подтверждение архитектуры)

```
UI меняет настройку (день готовки, anchor date, ...)
        │
        ▼
POST /api/actions/<действие>  (намерение, НЕ пересчитанные данные)
        │
        ▼
Backend:
  1. валидирует вход
  2. сохраняет settings в SQLite (только их — расписание не кэшируется)
  3. вызывает planner.recompute(settings, today) — чистая Python-логика
  4. отдаёт полный новый AppState в ответе
        │
        ▼
UI заменяет весь локальный state на пришедший AppState → ре-рендер
```

Два варианта уведомления UI об изменении:

- **Синхронный (рекомендуется для старта, Фаза 2).** Мутация — это единственный
  триггер пересчёта; ответ на действие уже содержит новый AppState. Никакого
  отдельного канала не нужно, минимум сложности, полностью соответствует
  однопользовательскому сценарию (один браузер).
- **Push через WebSocket/SSE (Фаза 4, опционально).** Нужен только если
  несколько вкладок/устройств должны видеть изменения друг друга в реальном
  времени. Backend после пересчёта шлёт `{"event": "state_changed", "version": N}`
  всем подключённым клиентам, те делают `GET /api/state` заново.

Начинать стоит с синхронного варианта — он проще, и в 90% случаев (один человек,
один браузер) push не даёт ничего сверх обычного ответа на запрос.

## 1. Доменные структуры данных (`src/meal_planner/core/models.py`)

Чистые Python dataclasses (`frozen=True, slots=True`), без зависимости от
FastAPI/Pydantic/SQLite. Приведено к `meal-plan.jsx` в тикете 1.2; источник
истины — сам `models.py`, здесь — сводка.

```python
class MealKind(StrEnum):            # BREAKFAST / LUNCH / DINNER
ShoppingTiming = Literal["same", "before"]

Ingredient(name, qty: float, unit: str, category)   # unit всегда строка, "шт" тоже
RecipeStorage(keep, pan, micro, after: str | None)  # хранение и разогрев, только у обедов/ужинов
Recipe(id, name, kind: MealKind, kcal, protein,
       ingredients: tuple[Ingredient, ...], steps: tuple[str, ...],
       storage: RecipeStorage | None = None, is_fish: bool = False)

Settings(meal_anchor_date: date, cook_count, cook_weekday1, cook_weekday2: int | None,
         shopping_timing: ShoppingTiming)       # cook_weekday2 игнорируется при cook_count=1

DayMeals(date, cycle_index,                    # 1..5 после сортировки по fishPriority
         breakfast: Recipe, lunch: Recipe, dinner: Recipe,
         kcal_total, protein_total,
         is_day_zero: bool,                    # anchor - 1: готовка, меню нет
         is_cook_day: bool)                    # день 0 или день недели готовки

ShoppingItem(name, qty: float, unit: str, category)
ShoppingGroup(category, items: tuple[ShoppingItem, ...])   # группы в порядке CAT_ORDER
CookItem(lunch: Recipe, dinner: Recipe, portions: int)     # пара одной позиции ротации

ShoppingTrip(shopping_date, cook_date,
             window_start, window_end,          # cook_date+1 .. следующая готовка включительно
             cook_items: tuple[CookItem, ...], shopping_groups: tuple[ShoppingGroup, ...])

AppState(today, settings, schedule: tuple[DayMeals, ...], next_shopping_trip: ShoppingTrip,
         recipes: Mapping[str, Recipe], version: int)
```

Отличия от первоначального эскиза (все — по факту JSX): `unit` без `None`;
добавлены `RecipeStorage`, `ShoppingGroup`, `CookItem`, флаги `is_day_zero` и
`is_cook_day` (в JSX их считал компонент); последовательности — `tuple`.

## 3. Логика ротации и расписания (`src/meal_planner/core/scheduling.py`)

Портировать без изменения бизнес-правил (это уже проверенная логика,
менять поведение не нужно — только язык):

| JS-функция (оригинал)   | Python-эквивалент         | Назначение |
|---|---|---|
| `dishIndexForDate` | `dish_index_for_date` | какая из 5 позиций ротации приходится на дату |
| `breakfastForDate` | `breakfast_for_date` | чередование 2 завтраков через день |
| `fishPriority` | `fish_priority` | приоритет "рыбное блюдо — раньше в партии" |
| `nearestCookDate` / `previousCookDate` | те же | ближайшая дата готовки вперёд/назад от точки |
| `mealsForDate` | `meals_for_date` | главная функция: дата → (breakfast, lunch, dinner) с учётом сортировки по свежести |
| `dayTotals` | `day_totals` | сумма ккал/белка за день |

Дополнительно явно вынести:
- `build_schedule(settings, date_from, date_to) -> list[DayMeals]` — цикл по датам,
  вызывающий `meals_for_date` для каждой.
- `next_shopping_trip(settings, today) -> ShoppingTrip` — вычисление окна
  готовки/потребления и даты похода в магазин (с учётом `shopping_timing`).
  Живёт в `planner.py`: собирает данные из `scheduling` и `shopping`.

**Важно:** это чистые функции без побочных эффектов — идеальные кандидаты для
unit-тестов. Перед портированием стоит зафиксировать 5-10 контрольных примеров
из текущего JS-поведения (конкретные даты → ожидаемые id блюд), чтобы Python-версия
дала идентичный результат — это защитит от случайного изменения логики при переносе.

## 4. Извлечение и агрегация списка покупок (`src/meal_planner/core/shopping.py`)

```python
def extract_shopping_list(day_meals: list[DayMeals]) -> tuple[ShoppingGroup, ...]:
    """
    Собирает все ингредиенты блюд за переданный период (обычно — окно
    следующей закупки), суммирует одинаковые (name, unit), группирует по category.
    Порядок групп фиксированный: Белок, Крупы, Овощи, Яйца и молочное, Прочее.
    """
```

Правила агрегации, которые нужно явно закрепить (в оригинале это было неявно
в JS-редьюсере):
- Суммируются только позиции с одинаковыми `name` **и** `unit`.
- Штучные позиции (авокадо "0.5 шт" + "0.25 шт") суммируются как обычные числа.
- Округление количества — вверх до 0.1 (ceil) по точной сумме (`Decimal`),
  сознательно вместо JS `Math.round` (решение в тикете 1.6): список покупок
  никогда не занижен.

## 5. Оркестрация (`src/meal_planner/core/planner.py`)

Единая точка входа, которую вызывает API-слой:

```python
def recompute(
    settings: Settings,
    today: date,
    date_from: date | None = None,
    date_to: date | None = None,
    version: int = 0,
) -> AppState:
    date_from = date_from or today
    # SCHEDULE_DAYS = 14, как PAGE_SIZE в JS
    date_to = date_to or date_from + timedelta(days=SCHEDULE_DAYS - 1)
    return AppState(
        today=today,
        settings=settings,
        schedule=build_schedule(settings, date_from, date_to),
        next_shopping_trip=next_shopping_trip(settings, today),
        recipes=ALL_RECIPES,
        version=version,
    )
```

Диапазон расписания произвольный (`GET /api/state?from=&to=`, «Перейти к
дате» в UI), а поездка в магазин — всегда от `today`.

Это единственная функция, которую дергает API при любой мутации настроек.

- `next_shopping_trip` строит дни своего окна сам (`build_schedule` по
  `window_start..window_end`), а не фильтрует `schedule`: окно поездки может
  закончиться через 13 дней после `today`, и короткое расписание дало бы
  неполный список покупок.
- `version` передаётся снаружи (из SQLite в API) — в `core/` нет состояния.

## 6. Персистентность (SQLite)

Минимальная схема — хранить нужно только `settings` (единственная строка,
как сейчас в `window.storage`) и опционально версию/снапшот для истории:

```sql
CREATE TABLE settings (
    id INTEGER PRIMARY KEY CHECK (id = 1),   -- singleton
    meal_anchor_date TEXT NOT NULL,
    cook_count INTEGER NOT NULL,
    cook_weekday1 INTEGER NOT NULL,
    cook_weekday2 INTEGER,
    shopping_timing TEXT NOT NULL,
    version INTEGER NOT NULL DEFAULT 1
);
```

Расписание/закупки **не кэшировать** в БД — это дешево пересчитать на лету
из settings, хранить их — источник рассинхрона. Кэшировать только если
профилирование покажет, что пересчёт дорогой (не должен: это чистая арифметика
над датами).

С фазы 5 в БД ещё и каталог — рецепты, ингредиенты, слоты цикла (см.
«Рецепты в БД (фаза 5)»). Расписание и покупки по-прежнему не кэшируются.

Слой доступа: `src/meal_planner/db/repository.py` — `get_settings()`, `save_settings(settings)`.
Путь к файлу БД берётся из переменной окружения `MEALPLAN_DB_PATH`.
Можно на голом `sqlite3`, ORM (SQLAlchemy) не обязателен при одной таблице.

## 7. API-слой (`src/meal_planner/api/main.py`, FastAPI)

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| GET | `/api/state?from=&to=` | — | полный `AppState` (JSON) для запрошенного окна дат (по умолчанию 14 дней с `today`) |
| GET | `/api/recipes` | — | справочник всех рецептов |
| POST | `/api/actions/set-cook-schedule` | `cook_count`, `cook_weekday1`, `cook_weekday2?` | обновлённый полный `AppState` |
| POST | `/api/actions/set-shopping-timing` | `shopping_timing` | обновлённый полный `AppState` |
| POST | `/api/actions/set-anchor-date` | `meal_anchor_date` | обновлённый полный `AppState` |
| POST | `/api/actions/set-nutrition-target` | `daily_kcal_target`, `daily_protein_target` (оба, `null` — цели нет; 8.1) | обновлённый полный `AppState` |

Действия принимают те же `?from=&to=`, что и `GET /api/state`. Общий путь
обработки (`apply_action` в `api/main.py`):
1. Проверить диапазон дат (`from ≤ to`, не больше 366 дней).
2. Взять текущие settings из БД (или дефолты, пока ничего не сохранено).
3. Применить действие — чистая функция из `core/actions.py`.
4. Провалидировать итоговые settings (`core/validation.py`); при ошибке — 422
   в формате FastAPI, ничего не сохраняется.
5. `save_settings(...)` → новая `version`.
6. `recompute(...)` → вернуть `AppState` как JSON.

`POST /api/shopping/remaining` (8.2) — не действие: тело с остатками из
счётчиков HA, ответ — ближайшая закупка за вычетом остатков. Остатки — вход
расчёта, как `today`, а не состояние: в SQLite не пишутся, `version` не
меняется. Вкладка «Закупки» показывает полный список по плану.

`GET /api/cookbook` (9.1) — только чтение, как `/api/summary`: ближайшая
готовка (блюда с порцией под цель) и активные рецепты по видам с шагами — для
сенсора вкладки «Рецепты» HA. Первый запрос, как и summary, сохраняет дефолты.

Универсального `PATCH /api/settings` нет — см. «Делать» ниже и
`ARCHITECTURE.md`. Новая мутация — новое атомарное действие.

Сериализация: Pydantic-модели в `api/schemas.py` как DTO поверх доменных
dataclasses; дни и cook items ссылаются на рецепты по id.

## 8. Frontend: что меняется

`MealPlanApp.tsx` сейчас сам вызывает JS-версии `mealsForDate`, `dayTotals` и
т.д. — это нужно убрать. Новая логика компонента:

- При маунте и при смене видимого диапазона дат → `GET /api/state?from=...&to=...`,
  результат кладётся в state как есть.
- Любое изменение в разделе "Настройки" (день готовки, anchor date, таймингы
  закупки) → соответствующий `POST /api/actions/...`, ответ **целиком заменяет** текущий `AppState`
  в компоненте (никакого локального пересчёта).
- **Все URL к API — относительные** (`fetch('api/state')`, без ведущего `/`),
  и `base: './'` в `vite.config.ts`. Иначе приложение не заработает за
  Home Assistant Ingress, который отдаёт его под динамическим префиксом.
  Эта проверка дешёвая сейчас и дорогая потом.
- Вкладки "Расписание"/"Меню"/"Закупки" становятся чисто презентационными —
  просто читают готовые поля из `AppState.schedule` / `.next_shopping_trip`.

Это устраняет дублирование бизнес-логики между JS и Python и делает Python
единственным источником истины — то, что вы и описали.

## 9. Тестирование

- `tests/test_scheduling.py` — golden-тесты: фиксированные `settings` + даты →
  ожидаемые id блюд/завтраков, снятые с текущего работающего JS-приложения
  (прогнать несколько сценариев в браузере, записать результат как fixture).
- `tests/test_shopping.py` — агрегация: два рецепта с общим ингредиентом →
  проверить, что суммируется, а не дублируется.
- `tests/test_architecture.py` — через `ast` проверяет, что модули в
  `src/meal_planner/core/` не импортируют `fastapi`, `pydantic`, `sqlite3`,
  `meal_planner.api`, `meal_planner.db`.
- `tests/test_api.py` — `POST /api/actions/set-cook-schedule` меняет `cook_weekday1` →
  `next_shopping_trip.cook_date` действительно сдвигается на нужный день недели.

## Делать

- Держать **весь** расчёт (ротация блюд, календарь, агрегация покупок) внутри
  `core/`, вызываемым из API-слоя. Ничего из этой логики не дублировать во
  фронтенде — даже "по мелочи, чтобы UI не мигал". Это единственное условие,
  при котором прикрутить Home Assistant или любого другого клиента API позже
  будет дёшево (см. раздел "Home Assistant integration" ниже).
- Проектировать мутации как **атомарные действия с понятным смыслом**
  (`POST /api/actions/skip-next-cook`, `POST /api/actions/set-cook-day`),
  а не как один универсальный `PATCH /api/settings`, принимающий произвольный
  diff. Атомарные действия проще тестировать, проще описать для голосового
  ассистента как tool, и не требуют от вызывающей стороны знать внутреннюю
  структуру `Settings`.
- Зафиксировать golden-тесты (входные `settings` + дата → ожидаемые id блюд)
  **до** переноса логики на Python — по текущему работающему JS-поведению.
  Это единственная защита от случайного изменения бизнес-правил при портировании.
- Хранить в SQLite только `settings` (источник истины) — расписание и список
  покупок всегда пересчитывать на лету из `planner.recompute()`. Кэш расписания
  в БД — источник рассинхрона, а не оптимизация (пересчёт дешёвый).
- Держать доменный слой (`core/`) свободным от FastAPI/Pydantic-специфики —
  чистые dataclasses и функции, тестируемые без поднятия сервера.
- Закрепить границу слоёв **автоматической проверкой**, а не только словами в
  CLAUDE.md: `tests/test_architecture.py` падает, если в `core/` появился
  импорт `fastapi`, `pydantic`, `sqlite3`, `meal_planner.api` или
  `meal_planner.db`.
- Брать все пути и порты из переменных окружения (`MEALPLAN_DB_PATH`,
  `MEALPLAN_STATIC_DIR`, `MEALPLAN_PORT`) — условие лёгкого Docker-образа,
  который запускается рядом с Home Assistant.
- Во фронтенде использовать только **относительные URL** и `base: './'`.
- Готовить эндпоинты так, будто у них будет больше одного клиента (браузер +
  в перспективе HA) — это не оверинжиниринг, а просто следствие "делать".

## Избегать

- Не считать что-либо (сегодняшнее меню, дату следующей закупки, итоги ккал)
  в React-компоненте "для скорости отклика". Это и есть тот единственный
  реальный риск для будущей HA-интеграции — дублирование логики, которое
  придётся находить и убирать задним числом.
- Не добавлять WebSocket/SSE-пуш в первой итерации. Он не нужен, пока нет
  сценария "два устройства смотрят план одновременно" — усложняет API без
  пользы на старте (см. раздел 0).
- Не откладывать базовую аутентификацию до момента, когда бэкенд реально
  выложат за пределы Ingress/локальной сети — если это вообще в горизонте
  планов, дешевле добавить простой middleware заранее.
- Не хранить пересчитанное расписание/шоппинг-лист в БД "на всякий случай для
  скорости" — это создаёт вторую версию правды рядом с `settings` и требует
  инвалидации при каждом изменении настроек.
- Не проектировать `PATCH /api/settings` как единственный способ мутации —
  если голосовой ассистент (или любой другой клиент) должен будет сам
  вычислять diff настроек, это хрупко и плохо описывается моделью как tool.
- Не использовать абсолютные URL (`/api/...`, `/assets/...`) во фронтенде —
  они ломаются за Ingress. Только относительные пути и `base: './'`.
- Не хардкодить путь к БД, порт и каталог статики в коде.
- Не дробить проект на несколько Python-пакетов / uv workspace и не выносить
  `core` в отдельный дистрибутив — одного пакета с подпакетами достаточно.
- Не переносить JS-логику "по смыслу" — переносить 1:1 со сверкой по golden-тестам,
  особенно `fishPriority`/`mealsForDate` (там неочевидная сортировка) и
  агрегацию количеств (`fmtQty`) — расхождение в округлении незаметно в коде,
  но заметно в реальном списке покупок.

## 10. Фазы реализации (для Claude Code — по одной фазе за раз)

0. **Скаффолдинг.** uv-проект с раскладкой `src/meal_planner/`, зависимости,
   конфиг pytest/ruff, `uv.lock`.
1. **Домен + тесты.** `src/meal_planner/core/models.py`, `recipes_data.py`,
   `scheduling.py`, `shopping.py`, `planner.py`. Без FastAPI, без SQLite.
   Юнит-тесты зелёные, логика проверена против golden-примеров, граница

2. **Backend API.** SQLite-репозиторий настроек + FastAPI-эндпоинты

3. **Frontend rewiring.** Заменить JS-расчёты в `MealPlanApp.tsx` на вызовы

6. **Тюнинг (после порта).** Поведение меняется сознательно, а не 1:1 с

## Рецепты в БД (фаза 5)

Решения тикета 5.1 (2026-10-27). Неизменные правила: ккал и белок считает
`core/` из ингредиентов, мутации — атомарные действия, `core/` получает
данные параметром, id рецептов (`l1`, `d3`, …) сохраняются, без правок план
и покупки те же, что до фазы.

### Модель

- **Ингредиент справочника.** Одна единица и одна категория на ингредиент
  (в сид-данных так у всех 37, поэтому ключ агрегации покупок
  `name|unit|cat` вырождается в ингредиент). Единицы — фиксированный набор
  `г, мл, шт, ст.л., зубчик`; категории — `shopping.CATEGORY_ORDER`, не
  редактируются. Название уникально, переименовывать можно — рецепты
  ссылаются по id. Единицу ингредиента, который есть в рецептах, не менять
  (поменялся бы смысл количеств). Удаления в фазе 5 нет.
- **Рецепт.** Тип (`breakfast | lunch | dinner`) задаётся при создании и не
  меняется. Id нового рецепта выдаёт сервер: префикс типа и следующий
  свободный номер (`l6`, `d6`, `b4`). Ккал и белок не хранятся.
  Комментарии-подсказки сида («½ перца») в БД не переносятся.
- **Статус** — `active | archived`; в 8.6 добавится `draft`. Рецепт из
  слота не архивируется, архивный в слот не ставится.
- **Цикл** — 5 слотов «обед + ужин» (позиция 1..5). Рецепт может стоять в
  нескольких слотах. `fish_priority` и пара обед↔ужин в
  `next_shopping_trip` берут слоты вместо `LUNCH_IDS`/`DINNER_IDS`.
- **Завтраки** — ротация остаётся константой b1/b2 по чётности дня, слотов
  завтраков нет. Бенедикт выделен из b1 в b3 (5.1a) и стоит только в пуле.

Схема — `src/meal_planner/db/schema.py` (5.2): таблицы `ingredients`,
`recipes` (со `status`), `recipe_ingredients` и `recipe_steps` (с
`position`), `cycle_slots` (1..5). Ккал не хранятся. CHECK — только на
неизменные наборы (тип блюда, слот 1..5, количество > 0); статус и единицы
проверяет `core/`, иначе `draft` (8.6) потребовал бы пересоздания таблицы.
Порядок рецептов `rowid` не задаёт (`VACUUM` его меняет у таблиц без
`INTEGER PRIMARY KEY`) — его определяет 5.3.

Миграции — `PRAGMA user_version`: `MIGRATIONS` в `db/schema.py`, i-я
доводит БД до версии i + 1 в одной транзакции с `user_version`
(`BEGIN IMMEDIATE`). 1 — `settings` (с догоном колонки 7.7 для старых БД),
2 — каталог и сид. Сид — часть миграции 2: каталог заполняется ровно один
раз, правки пользователя не перезатираются. Сид собирает
`core/seed.py` из `recipes_data.py`, `nutrition.py` (источник — третий
элемент `PER_100G`), `STORE_PIECES` и `LUNCH_IDS`/`DINNER_IDS`. БД новее
приложения (откат образа после миграции) не открывается — `SchemaTooNewError`;
откат образа — вместе с бэкапом БД до обновления.

### Каталог в `core/` (5.3)

`core/` не импортирует справочники: `Catalog` (рецепты с ккал, справочник
ингредиентов по названию, слоты) приходит первым параметром —
`recompute(catalog, settings, today, …)`, `build_schedule`, `meals_for_date`,
`today_position`, `next_shopping_trip`, `extract_shopping_list`,
`aggregate`, `set_cycle_position`. Собирает его `core/catalog.build_catalog`
из справочника, `RecipeSpec` (рецепт без ккал) и слотов — одинаково для БД
(`SettingsRepository.get_catalog`, читается на каждый запрос) и для сида
(`core/seed.SEED_CATALOG`, на нём golden и тесты core). Порядок рецептов —
тип (завтрак, обед, ужин), затем номер id. «Что готовить» группируется по
позиции ротации: обед и ужин — из слота.

### Действия

| Действие | Тело | Правила (422 по-русски) |
|---|---|---|
| `save-recipe` | рецепт целиком; без `id` — создать | ингредиенты из справочника, количество > 0, ингредиент не дважды; ≥ 1 шаг; у обеда/ужина `keep`/`pan`/`micro`; тип не меняется |
| `archive-recipe` | `{id}` | рецепт не в слоте |
| `restore-recipe` | `{id}` | — |
| `set-cycle-slot` | `{slot, lunch_id, dinner_id}` | slot 1..5; активные рецепты своего типа |
| `save-ingredient` | ингредиент; без `id` — создать | единица и категория из наборов; `grams_per_unit` для не г/мл; единица не меняется, если ингредиент в рецептах |

Ответ: `save-recipe`, `archive-recipe`, `restore-recipe` —
`{state: AppState, recipe}` (рецепт с ккал и `status`); `save-ingredient` —
`{state, ingredient}`; `set-cycle-slot` — `AppState`. Любое действие в одной
транзакции с записью увеличивает общий `version` — каталог меняет план;
если настроек ещё нет, их дефолты сохраняются первыми (как при первом
`GET`). Правила — `core/catalog_actions.py`, ошибки все сразу с `loc` до
поля; `archive`/`restore` идемпотентны, завтраки ротации b1/b2 не
архивируются. `GET /api/ingredients` — справочник с `used_in`.

### Редактор и предпросмотр ккал (5.5)

Редактор — в «Настройки → Блюда», на весь экран. Ккал и белок черновика —
`POST /api/recipes/preview {ingredients: [{ingredient_id, qty}]}` →
`{kcal, protein}`: тот же `nutrition()` по справочнику, недописанные строки
(не выбран ингредиент, количество ≤ 0) не считаются. Только чтение — версия
не меняется, правило «мутации — только действия» не задето. Фронтенд шлёт
запрос через 300 мс после правки строк и отбрасывает устаревшие ответы.

### Цикл и справочник в «Настройках» (5.6)

Состав цикла — `AppState.cycle_slots` (ответ `set-cycle-slot` — `AppState`);
позиция меняется сразу при выборе. `GET /api/ingredients` отдаёт
`{ingredients, units, categories}`: единицы и категории — правило `core/`
(`UNITS`, `CATEGORY_ORDER`), форма ингредиента их не дублирует. Пустые ккал
и белок формы приходят `null` — «Укажите …» проверяет `core/`. После правки
ингредиента фронтенд перезапрашивает справочник рецептов (названия и ккал).

### Правка рецепта, под который уже куплено

Применяется сразу, UI предупреждает. Признак считает `core/`
(`planner.plan_use`) и отдаёт в `AppState.recipe_plan_use`, а не в
справочнике рецептов: тот фронтенд грузит один раз, а признак меняется с
датой и после действий. `plan_use` — `bought`, если рецепт съедается между сегодня и началом окна
ближайшей закупки (`next_shopping_trip.window_start` − 1, продукты уже
куплены); `next_trip`, если он в `cook_items` ближайшей закупки (изменятся
список и to-do HA после синхронизации 7.8); иначе `null`.

## Home Assistant integration (фаза 7)

Home Assistant при таком API — просто ещё один клиент `/api/state` и
`/api/actions/*`, изменений в `core/` не требует.

**Установка HA — в Docker (HA Container).** Supervisor'а нет, а с ним нет
add-on'ов, Ingress и бэкапов add-on'ов. Целевая схема — два независимых
контейнера на одном хосте:

```
Хост (Docker)
├── homeassistant           (обычно network_mode: host)
│     YAML-пакет: rest-сенсоры, rest_command, скрипты для Assist,
│     UI приложения в боковой панели (см. варианты ниже)
└── meal-planner            (этот репо: FastAPI + core/ + SQLite + фронтенд)
      порт 8000, БД в своём томе/каталоге, TZ как у HA,
      restart: unless-stopped, HEALTHCHECK
```

UI в боковой панели — **решено в spike 7.1 (2026-10-26): `hass_ingress`.**

Варианты и почему не они:
- **Дашборд «Веб-страница»** (iframe) на `http://<хост>:8000/`. Сейчас HA
  открывается только дома или через VPN по http, так что mixed content не
  мешает. Но приложение открыто всей LAN без логина. Если HA когда-нибудь
  откроется по https, http-iframe браузер заблокирует. Запасной вариант,
  если `hass_ingress` перестанет поддерживаться.
- **Свой reverse proxy** с https и аутентификацией. Отдельный сервис ради
  одного приложения — избыточно, пока HA не выставлен наружу.

**`hass_ingress`** ([lovelylain/hass_ingress](https://github.com/lovelylain/hass_ingress),
HACS) — Ingress-подобный прокси внутри HA. На 2026-10 проект активен
(v1.3.x, коммиты в 2026), поддерживает HA 2025.8+ (там у каждой панели
своя строка интеграции). Что даёт:
- **Защита:** панель доступна только под логином HA (токен пользователя в
  cookie), `require_admin` по желанию. `static_token` (публичная ссылка в
  обход логина) не использовать. Работает и в Companion-приложении, и
  снаружи — везде, где открывается сам HA.
- **Префикс:** `work_mode: ingress` отдаёт приложение под
  `/api/ingress/<name>/`, срезает префикс и шлёт `X-Ingress-Path`. Это ровно
  то, что моделирует стенд `tools/ingress-test` (тикет 3.5): относительные
  URL и `base: './'` уже работают. Заголовок приложению не нужен.
- **Риск:** сторонняя интеграция, обновления через HACS. Если проект
  заглохнет — откат на дашборд «Веб-страница» без изменений в приложении.

Конфигурация (7.2), YAML или UI интеграции:

```yaml
ingress:
  meal_planner:
    title: Питание
    icon: mdi:food
    work_mode: ingress
    url: http://127.0.0.1:8001      # host-сеть HA, порт из compose ниже
```

**На каком интерфейсе слушает порт** — зависит от сети контейнера HA
(проверить: `docker inspect <ha> --format '{{.HostConfig.NetworkMode}}'`):
- **HA в `network_mode: host`** (типично): публиковать порт только на
  loopback хоста — `ports: ["127.0.0.1:8000:8000"]`. Из LAN приложение не
  видно, HA ходит на `http://127.0.0.1:8000`.
- **HA в docker-сети**: meal-planner в той же сети, порт на хост не
  публиковать вовсе; HA ходит на `http://meal-planner:8000`.

В обоих случаях внутри контейнера uvicorn слушает `0.0.0.0:$MEALPLAN_PORT`
(entry point `meal-planner`), ограничение — на уровне публикации порта.

**Развёртывание (7.2, 2026-10-26; пошагово — README, «Развёртывание рядом с Home Assistant»).** У пользователя HA в `network_mode: host`
(`/opt/docker-compose.yaml`, весь стек в одном файле). Порт 8000 на хосте
не берём: Portainer там тоже в host-сети и держит 8000 (Edge tunnel), 9000,
9443. Сервис — в тот же общий compose:

```yaml
  meal-planner:
    container_name: meal-planner
    build: /home/valentinart/meal-planner   # клон репо вне /opt (там git HA-конфигов)
    image: meal-planner:local
    restart: unless-stopped
    ports:
      - "127.0.0.1:8001:8000"               # только loopback: HA в host-сети
    volumes:
      - /opt/meal-planner-data:/data        # chown 10001:10001, бэкап — 7.4
      - /etc/localtime:/etc/localtime:ro    # «сегодня» в той же зоне, что у HA
```

- Образ собирается на хосте из клона (репо приватный — deploy key только
  на чтение). Реестр не нужен; обновление — `git pull` и
  `docker compose up -d --build meal-planner`.
- `/opt/meal-planner-data` в git HA-конфигов не попадает: `.gitignore` там
  по белому списку.
- TZ — монтированием `/etc/localtime`, как у HA. tzdata в образе есть,
  проверено.
- `HEALTHCHECK` в Dockerfile ходит в `GET /api/health` (только чтение БД).
  Docker без Supervisor'а unhealthy-контейнер **не перезапускает** — статус
  только виден в `docker ps`/Portainer; перезапуск — при падении процесса
  (`restart: unless-stopped`).

Остальное:
- **Бэкап (7.4, решено 2026-10-26).** Бэкапы HA на хосте не настроены, а
  наш каталог в них и не попал бы. Поэтому свой бэкап:
  - `meal-planner-backup` (entry point пакета, `db/backup.py`) снимает копию
    через backup API `sqlite3` (как `.backup`, утилита в образе не нужна),
    проверяет её `integrity_check`, пишет атомарно в
    `<каталог БД>/backups/mealplan-YYYYmmdd-HHMMSS.db`, хранит последние
    `--keep` (14) копий;
  - запуск — cron на хосте раз в сутки:
    `30 3 * * * docker exec meal-planner meal-planner-backup 2>&1 | logger -t meal-planner-backup`;
  - копии на том же диске (`/opt/meal-planner-data/backups`): защищают от
    неудачного действия и порчи файла, но не от потери диска — сознательно;
  - права каталога: владелец 10001 (приложение), группа `valentinart`,
    `2750` — setgid, чтобы новые копии тоже читались через sshfs; писать
    может только контейнер. `chown -R` на `valentinart` ломает приложение:
    в `750`-каталог uid 10001 не войдёт, любой запрос — 500;
  - восстановление — README, «Бэкап и восстановление».
- **Watchdog:** без Supervisor'а это задача Docker — `HEALTHCHECK` и
  `GET /api/health`, плюс `restart: unless-stopped`.
- **Доступ HA к API** (REST-сенсоры, `rest_command`): по тому же внутреннему
  адресу, что и `hass_ingress` (`http://127.0.0.1:8001`), напрямую, без аутентификации. Снаружи этот
  адрес недоступен (см. публикацию порта выше), так что отдельная защита API
  не нужна.
- **Компактный `GET /api/summary` для REST-сенсоров (7.5):** `/api/state`
  весит ~6 КБ и ссылается на рецепты по id, а у сенсора `state` — строка
  до 255 символов. Ответ (~2.5 КБ):

  ```
  today, version
  days.today / days.tomorrow: date, breakfast, lunch, dinner (названия или
      null до старта и в день 0), kcal, protein, is_cook_day, is_day_zero,
      is_before_start
  next_shopping: date, cook_date, window_start, window_end,
      cook  — ["обед + ужин — x1", …]          (как «Что готовить» в UI)
      items — ["авокадо — 200 г (≈ 2 шт)", …]  (как «Что купить», по категориям)
  ```

  Строки форматирует API-слой (`api/schemas.py`), `core/` не меняется.
  `items` — вход и для to-do HA (7.8).
- **Пакет HA (7.6):** `ha/packages/meal_planner.yaml` в этом репо. В HA он
  попадает bind mount'ом из клона:
  `/home/valentinart/meal-planner/ha/packages:/config/packages/meal_planner:ro`,
  плюс `homeassistant: packages: !include_dir_named packages`. `git pull`
  обновляет пакет, после чего нужен перезапуск HA. `tests/test_ha_package.py`
  сверяет URL, поля тел и пути шаблонов с `openapi.json`. Состав:
  - `rest`-сенсоры `sensor.meal_planner_today` / `_tomorrow` (state — «Обед: …
    Ужин: …») и `sensor.meal_planner_next_shopping` (дата; `cook`, `items` в
    атрибутах), `scan_interval` 15 мин. После действия скрипт делает
    `update_entity`;
  - `rest_command` на summary и три действия;
  - скрипты-tools для LLM: `meal_planner_plan` возвращает summary целиком
    (`stop` + `response_variable`); действия возвращают `{ok}` или
    `{ok: false, error}` с русским текстом ошибки из core;
  - локальные фразы (`conversation: intents` + `intent_script`): «что сегодня
    / завтра на обед», «когда закупка». Отвечают из сенсоров, без LLM.
- **Пропуск готовки (7.7)** — пауза цикла, а не сдвиг якоря. Сдвиг якоря
  поменял бы блюда уже сваренного окна. Правило (`scheduling.meals_for_date`
  с `skipped`):
  - дни до пропущенной готовки C — как были; в день C не готовим;
  - C+1 … N (N — следующая готовка) — пауза без блюд;
  - после N — якорь + (N − C), то есть тот же цикл с того же блюда;
  - закупка — к N.

  Хранится один пропуск, в `settings`. Новые колонки добавляет
  `SettingsRepository._migrate` (`PRAGMA table_info` + `ALTER TABLE`).
- **Список покупок в to-do (7.8):** скрипт `meal_planner_sync_shopping_list`
  переносит `next_shopping['items']` в Local To-do «Покупки». Метка
  `meal-planner <дата закупки>` в описании пункта отличает свои пункты и их
  закупку. Поэтому синхронизация идемпотентна, купленное не возвращает и не
  трогает пункты пользователя. Автоматизация — в 07:00 в день закупки.
- **Почему LLM получает данные из скрипта, а не из атрибутов:** в живой
  контекст модели (`_get_exposed_entities` в `homeassistant/helpers/llm.py`)
  попадают состояние и только белый список атрибутов (`temperature`,
  `brightness`, …). Атрибуты с блюдами и покупками модель не видит.
- **Expose** сенсоров и скриптов для Assist хранится в `.storage`, а не в
  YAML: включается руками в «Голосовые ассистенты → Открыть доступ».
- Для этого и нужны атомарные action-эндпоинты (см. «Делать» выше).
- Что уже заложено: относительные URL + `base: './'`, конфиг через env,
  Dockerfile на `uv sync --frozen`, образ под amd64 и aarch64 (переезд с
  Wyse на Pi-класс железо).

**Если HA когда-нибудь переедет на HAOS / Supervised**, приложение
становится local add-on:
- `config.yaml` с `ingress: true`, `ingress_port: 8000`,
  `arch: [amd64, aarch64]`;
- БД в `/data`, которая попадает в бэкапы HA;
- Ingress даёт аутентификацию и префикс, стенд 3.5 проверяет ровно это.

Нюансы:
- Supervisor собирает local add-on только из его папки — нужна сборка
  папки с копией `src/`/`frontend/` или готовый образ в реестре (`image:`);
- `/data` add-on'а принадлежит root, а образ работает под uid 10001.

## Рецепты на дашборде «Кухня» (фаза 9)

Обсуждение 2026-10-28. На «Кухне» (YAML-дашборд HA, Metro-плитки на
button-card + layout-card) есть «Запасы» и «Готовка», а рецепта нет: он
только в приложении. Нужна вкладка «Рецепты»: блоки «Ближайшая готовка»,
«Обеды», «Ужины», «Завтраки»; касание плитки раскрывает рецепт — плитка
уходит влево, справа шаги и ингредиенты.

### Решения пользователя

- В HA на button-card, не во фронтенде meal-planner.
- Отдельный вид «Рецепты», только чтение; «Готовка» (MT-9) не меняется.
- Все активные рецепты (без черновиков и архива), первым рядом —
  «Ближайшая готовка».
- Ингредиенты на 1 порцию: у ближайшей готовки — порция под цель (8.5), в
  группах — базовая.
- Дизайн по прототипу (https://claude.ai/artifact/3C6xhPVaHTx8vi3WTpFLCA):
  анимация входа панелей и FLIP-перестройка есть. Куда встаёт раскрытая
  плитка — опция `expand`: `inplace` (на своей строке), `group` (под
  заголовком своей группы, по умолчанию), `screen` (над всеми группами).

### Реализуемость в HA

| Что нужно | Чем | Итог |
|---|---|---|
| Плитки, группы, телефон/ПК | layout-card + mediaquery, как «Запасы» | повторяем готовое |
| Шаги и ингредиенты | в HA их нет: `cook_batch` — только `name/portions/cooked` | endpoint + сенсор (9.1, 9.2) |
| Раскрытие | весь вид — одна button-card с плоской сеткой (заголовки групп — строки на всю ширину); `<details name>` — один открытый рецепт на вид без JS; `:has()` растягивает открытое на строку, CSS `order` ставит его по опции `expand` | прототип готов, перенос — MT-10 |
| Анимация панелей | `@keyframes`: шаги и ингредиенты выезжают справа с задержкой | CSS |
| Перестройка плиток (FLIP) | на CSS нельзя; JS в шаблоне поверх DOM: замер `getBoundingClientRect` до и после переключения `details`, `element.animate` — плитка едет в начало строки, соседи на новые места, высота группы плавно. Внутренности button-card не нужны: shadow root открыт, перерисовки нет | ~50–70 строк JS, спайк MT-10 |
| Открытое не схлопывается при обновлении | lit `unsafeHTML` не трогает DOM при той же строке (в коде button-card 7.0.1 так и есть) | проверить вживую в MT-10 |
| Текст из редактора/Assist | `esc()` в шаблоне | обязательно |

card-mod и новые ресурсы HACS не нужны.

### HA или фронтенд

| | HA (button-card) — выбрано | Фронтенд (React) |
|---|---|---|
| Стиль Metro | родной для «Кухни» | чужой для приложения |
| Рядом с готовкой | соседняя вкладка с «Готовкой» и «Запасами» | отдельная панель; «приготовлено» не отметить — остатки только в HA |
| Анимация | FLIP JS-ом в шаблоне + вход панелей CSS | FLIP в React |
| Тесты | нет, ручная проверка на телефоне и ПК | vitest, снапшоты, `no-business-logic` |
| Поддержка | JS/HTML в YAML, кэш дашборда, версия button-card | обычный TSX, типы из API |
| Оценка | ~12–16 ч, риск в спайке | ~10–13 ч, риск низкий |

Цена одной карточки на весь вид: любое изменение данных сенсора
перерисовывает его, и открытый рецепт закрывается.

В button-card 7.0.1 нужны два обхода (стандартный DOM): `pointer-events:
auto` у карточки без действий (иначе класс `disabled` гасит касания) и
capture-слушатели со `stopPropagation()` для событий из `summary` — иначе
`actionHandler` отменяет раскрытие через `preventDefault` на `touchend` и
`click`.

Не прошёл MT-10 на iOS Companion (раскрытие, `:has()`, схлопывание при
перерисовке) — запасной путь: вкладка во фронтенде. 9.1 нужен в обоих
случаях. FLIP дёргается на телефоне — `flip: false`, остаётся вход панелей.

### Данные

`GET /api/cookbook` — только чтение, не action. «Ближайшая готовка» —
`upcoming_cook_date`: не раньше сегодня, до старта — день 0, пропущенная
(7.7) — конец паузы; без поправки `shopping_timing="before"` из
`trip_cook_date` — нужна готовка, а не закупка. Блюда — `batch_dishes`.
Ингредиент — только `{name, qty_display, unit}`, шаги и `storage` — только в
группах: сенсор и так самый большой в HA. Дашборд ничего не считает.

### Нагрузка на HA

Замеры 2026-10-28 по копиям БД recorder (10.6 дня, 2764 сущности) и живой БД
приложения (14 активных рецептов): книга ≈ 50 КБ + ≈ 5 КБ блок готовки.

| Что | Сейчас | Новый сенсор | Прирост |
|---|---|---|---|
| Изменения состояний | ~3 300 в сутки (спокойные дни) | 1–5 в сутки: опрос без изменений события не создаёт | ~0.05–0.1% |
| recorder | ~3–9 тыс. строк в сутки | 0 — сенсор исключён (атрибуты > 16 КБ recorder всё равно не пишет) | 0% |
| CPU | — | 96 опросов в сутки × (~15 мс API + ~7 мс разбор в HA) ≈ 2 с в сутки | <0.01% ядра |
| Память | все состояния ≈ 0.45 МБ | +55 КБ | ~0.01–0.02% процесса |
| Загрузка дашборда (все сущности целиком) | ≈ 440 КБ | +55 КБ | ≈ +12% |

Рецепт добавляет ~3.5–4 КБ. Если загрузка дашборда станет заметной — сенсор
со списком (~3 КБ, +0.7%), а шаги и ингредиенты — ответом скрипта при
раскрытии (больше JS в шаблоне, ~50 мс на открытие).

Попутно: 2484 из 2764 сущностей — старые BLE-трекеры из `known_devices.yaml`
(сканер давно выключен, файл читается при каждом запуске), 67% строк
recorder. После их уборки сущностей ~280, база загрузки дашборда вдвое
меньше, и тот же сенсор — ≈ +25% к ней.

## Упаковка и запуск

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `MEALPLAN_DB_PATH` | файл SQLite | `./data/mealplan.db` |
| `MEALPLAN_STATIC_DIR` | собранный фронтенд | `./frontend/dist` |
| `MEALPLAN_PORT` | порт uvicorn | `8000` |

- `frontend/` собирается в `frontend/dist` (`outDir` в `vite.config.ts`);
  FastAPI отдаёт каталог из `MEALPLAN_STATIC_DIR`, если он существует.
- `Dockerfile` (тикет 2.8): две стадии на `python:3.12-slim` — builder ставит
  зависимости через `uv sync --frozen --no-dev` и пакет non-editable, в
  рантайм копируется только `.venv`. Пользователь `app`, БД на томе `/data`.
  Образ собирается под `linux/amd64` и `linux/arm64`. Node-стадии пока нет —
  она добавится в тикете 3.1 вместе с `frontend/` и положит сборку в
  `/app/frontend/dist`.
